## 3. สูตรที่ใช้ทำนาย (และข้อจำกัดของมัน)

จาก benchmark บนเครื่องระดับเดียวกัน: `ms/โทเคน = 44.9 + 3.29 × (layer ที่อยู่บน CPU)`

**ข้อจำกัดที่ต้องระวัง:** ค่า 3.29 ms/layer ถูก fit บน **IQ2 (138 MB/layer)**
สำหรับ Q4 (259 MB/layer) เวลาต่อ layer บน CPU = 259 MB ÷ bandwidth ≈ **5.9 ms**

| สถานการณ์ (Qwen3.8-27B Q4) | เวลา/โทเคน | tok/s |
|---|---|---|
| 16 layer บนการ์ด (49 บน CPU) | ~255 ms | 3.9 (ตรงกับที่วัด) |
| 24 layer บนการ์ด (41 บน CPU) | ~220 ms | **~4.5** |
| กำไรจาก layer อย่างเดียว | | **+14.6%** |
| กำไรจาก threads (8→12) | | **+23.5%** |
| รวมทั้งสอง | | **~+41% → 5.4–5.5 tok/s** |

**กำไรหลักมาจาก threads ไม่ใช่ layer** — ตารางเดิมของผมระบุที่มาผิด

## 4. ลำดับความสำคัญใหม่: prefill มาก่อน decode

| อาการ | ตัวเลข | วินิจฉัย |
|---|---|---|
| prefill 27B | 1.4 tok/s | **ผิดปกติ** — 21 โทเคนใช้ 15 วินาที ไม่ใช่ขีดจำกัดฮาร์ดแวร์ แต่คือ paging (RAM 98%) |
| prefill 9B | 2.6 tok/s | เช่นเดียวกัน |

**prompt 2,000 โทเคนที่ 1.4 tok/s = 24 นาที** — นี่ทำให้งานเอเจนต์ทั้งหมดเป็นไปไม่ได้ และการแก้ paging อาจให้ผลมากกว่าการดัน decode จาก 3.9 → 5.5

⇒ **ระยะ 1 = แก้ paging** (`--mlock` / โหลดให้ RAM เหลือ ≥6GB / mmap ที่คุมได้) แล้ววัด prefill ใหม่ก่อนแตะอย่างอื่น

## 5. ทางเลือกที่ยังไม่ได้ทดสอบ: GLM-4.7-Flash (MoE)

ไฟล์ 19.02 GB อยู่ในเครื่องแล้ว (`glm4moelite`, 29.94B total / ~3B active, 47 layers, MIT)

**ทำไมน่าสนใจ:** dense อ่าน weights ทั้งก้อนทุกโทเคน (16.81 GB) แต่ MoE อ่านเฉพาะ expert ที่ถูกเลือก (~2–4 GB) ⇒ ที่ Q4 คุณภาพเดิม ความเร็วควรสูงกว่าหลายเท่า

**สถานะ:** ยังไม่ทดสอบ · ต้องมี RAM ว่าง ~20 GB · ใช้ `-ot` / `--n-cpu-moe` วาง attention บนการ์ด experts บน CPU

## 6. กติกาคุณภาพ (ต้องมีหลักฐาน ไม่ใช่ความเชื่อ)

- Q4_K_M **ไม่ใช่ lossless** — มันคือ 4.92 bits โดยเฉลี่ย

- **ยังไม่มีข้อมูลงานไทย/โค้ด** ซึ่งเป็นงานจริงของผู้ใช้

⇒ ก่อนยึด "ห้ามลดคุณภาพ" เป็นหลักการ ต้องมี **eval 20–30 ข้อจากงานจริง** (ไทย + โค้ด + tool-calling) ไว้ตัดสิน — งานนี้อยู่ในระยะ 2

## 9. ค้นพบหลัก (13 พ.ย. 2026, 02:50) — กำแพงไม่ใช่โมเดล แต่คือ VRAM ของเดสก์ท็อป

### ข้อเท็จจริงที่วัดได้

| การวัด | ค่า |
|---|---|
| VRAM ทั้งหมด | 8151 MiB |
| VRAM ที่แอปผู้ใช้ถืออยู่ (Chrome×2, Edge, Roblox, OMEN, Python) | **7119 MiB** |
| VRAM จริงที่เหลือให้โมเดล | ~1 GB |
| ที่ llama.cpp **คิดว่า** allocate บนการ์ด (`CUDA0 model buffer`) | 4458 MiB |
| VRAM ที่เพิ่มขึ้นจริงเมื่อโหลดโมเดล | **266 MiB** |
| ⇒ ถูก WDDM spill ลง RAM เงียบ ๆ | **~4192 MiB** |

### ทำไมมันสำคัญ
WDDM ยอมให้จอง VRAM เกินจริงได้ แล้วสลับหน้าลง RAM โดยไม่บอกใคร ⇒ โมเดล "อยู่บนการ์ด" ตามรายงาน แต่ความเร็วจริงเป็น RAM-speed
นี่คือเหตุที่ 9B ได้ 21.85 tok/s ไม่ใช่ ~50 และเป็นเหตุที่ ollama รายงาน "100% GPU" ทั้งที่ VRAM จริง 3.5/8 GB

### สิ่งที่ไม่มีเครื่องมือไหนทำ (และเป็นหน้าที่ของ OverSpec)
รายงานและบังคับ **VRAM budget จริง** ก่อนโหลด:
- อ่าน VRAM ที่แอปอื่นถืออยู่ (ไม่ใช่แค่ total − used)
- ตรวจว่า weights ถูก spill หรือไม่ โดยเทียบ buffer ที่จองกับ VRAM ที่เพิ่มจริง
- ถ้าที่ว่างไม่พอ → ลด layer/บริบท **แทนที่จะปล่อยให้ WDDM สลับเงียบ ๆ**

### ผลต่อตัวเลขที่วัดมาแล้ว
ทุกครั้งที่วัด 9B (13.11 / 19.77 / 21.85 tok/s) มีแอปถือ VRAM 6–7 GB อยู่ ⇒ **ตัวเลขเหล่านั้นคือ "เพดานตอนเครื่องไม่ว่าง" ไม่ใช่เพดานของฮาร์ดแวร์**
การวัดที่สะอาดต้องปิด Chrome/Edge/Roblox ก่อน แล้ว baseline VRAM จะเหลือ ~2 GB
