# บทที่ 0 — โมเดลถูก "โหลด" เข้าเครื่องได้อย่างไร

เอกสารนี้เขียนสำหรับคนที่ไม่เคยแตะ C/C++ เชิงลึก ใช้เวลาอ่าน 15 นาที และจบด้วยแบบฝึกที่รันบนเครื่องคุณได้จริง

## 0.1 ไฟล์โมเดลไม่ใช่โปรแกรม

`qwen3.8:27b` ในเครื่องคุณคือไฟล์ **17.7 GB** ที่ขึ้นต้นด้วยไบต์ 4 ตัวว่า `GGUF` (เราอ่านจากไฟล์จริงแล้ว)

ข้างในเรียงกันแบบนี้:

```
[ GGUF ][ version ][ จำนวน tensor ][ metadata: ชื่อโมเดล, จำนวน layer, ctx ]
[ tensor index: ชื่อ + มิติ + ชนิดข้อมูล + ตำแหน่ง offset ]
[ ข้อมูลดิบของ weights ทั้งหมด  ← 99% ของไฟล์อยู่ตรงนี้ ]
```

จุดสำคัญ: **ไม่มีโค้ดอยู่ในไฟล์นี้** การ "โหลดโมเดล" จึงไม่ใช่การรันอะไร แต่คือการ **ทำให้โปรเซสของเราเข้าถึงไบต์ก้อนนี้ได้** — แล้วค่อยเอาไปคำนวณ

## 0.2 สามวิธีที่จะเข้าถึงไฟล์ (และนี่คือหัวใจของ OverSpec)

```
                    ┌─────────────────────────┐
     17.7 GB  ────▶ │  NVMe  ~7 GB/s          │
                    └───────────┬─────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
  ① อ่านเข้าหมด            ② mmap                 ③ streaming
  read() เข้า buffer      map ไฟล์เป็นหน่วยความจำ   อ่านเองทีละก้อน
        │                       │                       │
        └───────────────────────┼───────────────────────┘
                                ▼
                    PCIe ~32 GB/s  →  VRAM 384 GB/s
                                   →  RAM   73 GB/s
```

| | ① อ่านเข้าหมด | ② mmap (ค่าเริ่มต้น llama.cpp) | ③ streaming |
|---|---|---|---|
| RAM ที่ถือ | 17.7 GB ทันที | เท่าที่ "แตะ" จริง | คุมเองทีละก้อน |
| เกิดอะไรตอนโหลด | อ่านทั้งไฟล์ (ช้า ~2.5 วิ ที่ 7 GB/s) | ไม่มีอะไรเกิดขึ้น — แค่ขอยืม address | เปิดไฟล์ค้างไว้ |
| เกิดอะไรตอนใช้ | เร็วสุด (อยู่ใน RAM แล้ว) | **page fault** ทุกครั้งที่แตะหน้าที่ยังไม่โหลด | อ่านตามที่สั่ง |
| ปัญหา | RAM หมด → เครื่องค้าง | OS แอบเอากลับดิสก์ได้ → กระตุก | ต้องเขียน I/O เอง |

**page fault คืออะไร:** หน่วยความจำถูกแบ่งเป็นหน้า (หน้า = 4 KB) ตอน mmap ยังไม่มีข้อมูลใน RAM เลย พอโค้ดอ่านหน้าไหน ซีพียูจะหยุดแล้วบอก OS ว่า "หน้านี้ยังไม่มี" → OS ไปอ่าน 4 KB จากดิสก์มาให้ แล้วค่อยไปต่อ — ครั้งแรกช้า ครั้งต่อไปเร็ว (เพราะอยู่ใน RAM แล้ว)

**page cache:** RAM ที่ OS ใช้เก็บหน้าที่เพิ่งอ่าน — โมเดล 17.7 GB จึงมักเข้าไปนอนใน page cache เงียบ ๆ นี่คือเหตุที่ "RAM 98%" ทั้งที่ไม่มีโปรแกรมไหนอ้างว่ากิน 17 GB

## 0.3 ทำไมทุกโทเคนต้องอ่าน weights ครบ

โมเดล dense ไม่มีทางลัด: จะได้ 1 โทเคน ต้องผ่านทุก layer และทุก layer ต้องอ่าน weights ของมัน

```
เพดาน tok/s = ขนาด weights ÷ แบนด์วิดท์ของที่เก็บ weights

ของเครื่องคุณ:  17.7 GB ÷ 73 GB/s = 0.24 วินาที/โทเคน = 4.1 tok/s
ที่วัดได้จริง:  3.93 tok/s   ← ตรงกัน (ประสิทธิภาพ ~95%)
```

ตัวเลขนี้คือเหตุผลว่าทำไม "เขียนโค้ดให้ดีขึ้น" ไม่ทำให้เร็วขึ้นมาก — **มีแต่การอ่านให้น้อยลง (quant) หรืออ่านครั้งเดียวให้ได้หลายโทเคน (speculative) ที่เปลี่ยนสมการ**

## 0.4 ทำไมเครื่องค้าง — และ mlock แก้อะไร

1. ทุกโปรเซสแย่ง RAM ก้อนเดียวกัน
2. โมเดลแตะหน้าใหม่เรื่อย ๆ → working set โตขึ้น → ไปเบียดแอปอื่น
3. OS ต้องเลือกใครจะถูก evict — บางครั้งเลือกหน้าของโมเดลเอง
4. พอแตะหน้าถูก evict → page fault → อ่านดิสก์ → ช้าลง → ยิ่งแตะยิ่งช้า = **thrash**

`mlock` (หรือ `SetProcessWorkingSetSize` บน Windows) คือการบอก OS ว่า "หน้ากลุ่มนี้ห้ามย้ายออก" — กัน thrash ได้ แต่ก็กันไม่ให้แอปอื่นใช้ RAM ก้อนนั้น **นี่คือเหตุที่ OverSpec ต้องกันไว้ 6 GB ไม่ใช่ใช้ให้เต็ม**

## 0.5 แล้วมันขึ้นการ์ดยังไง

```
RAM (หรือ mmap)  ──cudaMemcpy──▶  VRAM   ──kernel──▶  ผลลัพธ์
                     ↑
              ผ่าน PCIe ~32 GB/s
```

- `cudaMalloc` = จอง VRAM
- `cudaMemcpy` = ก๊อปขึ้นการ์ด (ช้ากว่า RAM 12 เท่า เพราะผ่าน PCIe)
- **pinned memory** = ล็อกหน้า RAM ไม่ให้ถูก evict ระหว่างก๊อป → เร็วขึ้นราว 2 เท่า
- `-ngl N` ใน llama.cpp = "ย้าย N layer ขึ้น VRAM" ส่วนที่เหลือคำนวณบน CPU

**ทำไมต้องวางให้ดี:** layer ที่อยู่บนการ์ดอ่านได้ 384 GB/s, layer ที่อยู่บน RAM อ่านได้ 73 GB/s — ต่างกัน 5.3 เท่า การวางผิดที่หนึ่ง layer จึงมีราคา

## 0.6 แบบฝึก 5 ข้อ (รันบนเครื่องคุณได้เลย)

### 1. อ่าน magic number ของไฟล์จริง
```powershell
$f = Get-ChildItem 'D:\Models\ollama\blobs' -File | Sort Length -Descending | Select -First 1
$fs = [IO.File]::OpenRead($f.FullName); $b = New-Object byte[] 4
$fs.Read($b,0,4) | Out-Null; $fs.Close()
[Text.Encoding]::ASCII.GetString($b)          # ต้องได้ GGUF
'{0:N1} GB' -f ($f.Length/1GB)                # ต้องได้ ~17.7 GB
```
**สิ่งที่ได้:** ไฟล์โมเดลคือ data ล้วน และเราอ่านหัวไฟล์ได้ด้วย 5 บรรทัด

### 2. คำนวณเพดานของเครื่องตัวเอง
`17.7 GB ÷ 73 GB/s = 0.24 วิ/โทเคน` → ถ้าวัดได้ต่ำกว่านี้มาก แปลว่ามีอะไรกิน bandwidth อยู่

### 3. ดู RAM ก่อน/หลังมีคนใช้โมเดล
```powershell
(Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory / 1MB
```

### 4. ดู working set ของโปรเซส
```powershell
Get-Process | Sort WorkingSet64 -Desc | Select -First 5 Name,@{n='GB';e={[math]::Round($_.WorkingSet64/1GB,2)}}
```

### 5. ดู page fault ว่าเกิดจริงไหม
```powershell
Get-Counter '\Memory\Pages/sec' -SampleInterval 2 -MaxSamples 3
```
**อ่านค่า:** ตัวเลขหลักร้อย-พันต่อวินาที = กำลัง thrash (อันตราย) · หลักสิบ = ปกติ

## 0.7 ศัพท์ที่ต้องรู้

| คำ | ความหมายสั้น ๆ |
|---|---|
| **GGUF** | รูปแบบไฟล์โมเดล: header + index + weights ดิบ |
| **mmap** | ขอยืม address ให้ไฟล์ดูเหมือนหน่วยความจำ |
| **page fault** | แตะหน้าที่ไม่มีใน RAM → OS ไปโหลดจากดิสก์ |
| **page cache** | RAM ที่ OS ใช้เก็บหน้าที่เพิ่งอ่าน |
| **working set / RSS** | RAM ที่โปรเซสใช้จริงตอนนี้ |
| **mlock** | ห้าม OS ย้ายหน้านี้ออกไปดิสก์ |
| **pinned memory** | RAM ที่ล็อกไว้เพื่อก๊อปขึ้นการ์ดได้เร็ว |
| **quant** | บีบตัวเลข weights ให้กินที่น้อยลง (Q8 → Q4 → Q3) |
| **prefill** | อ่าน prompt ทั้งก้อน (คำนวณขนานได้ → เร็ว) |
| **decode** | ออกทีละโทเคน (อ่าน weights ใหม่ทุกครั้ง → ช้า) |
| **KV cache** | ความจำของโมเดลต่อบทสนทนา โตตามความยาว context |
